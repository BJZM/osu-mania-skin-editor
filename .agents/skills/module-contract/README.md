# module-contract · 模块契约化 Skill

> 一个通用的 AI 编程助手 Skill：新增功能时，把代码要求按实现需求**模块化**成**原子模块**与**复合模块**，为每个模块写**接口卡**，维护一份**模块汇总地图**，并在动工前按**决策阶梯**分析复用——优先用现有模块**组合（拼凑）**出所需功能，能不新建就不新建。

一个给 AI 编程助手（agent）用的通用 Skill——在你每次要加新功能时，先用“模块接口契约”把需求结构化，让后续写出来的代码更可复用、更可测、更少重复。

---

## 它解决什么问题

AI 直接写代码时常常：

- 相同功能在不同文件里被**重复实现**，名字还各不相同；
- 跨模块**数据类型对不上**、接口用词漂移；
- 只能看到局部，看不到整个项目的模块边界；
- 写出的东西“看起来能跑”，但没有一种可验证的判断标准。

`module-contract` 在动工前把需求切成**明确的模块**，并用**接口卡**钉住每个模块的输入 / 输出 / 依赖 / 约束。这样：

- AI 只需对着**一个模块的接口卡**实现，不用吞下整个代码库；
- 每个模块都能被**单独测试、单独分派**；
- 接口卡成为**单一事实来源**，避免重复造轮子和接口漂移；
- 动工前自动走**决策阶梯**：直接复用 → 复合重组 → 换 adapter → 扩展 → 最少新增原子，能借已有的就借，能拼就不新建。

它复用 **deep module（深模块）** 的词汇与方法，强调“接口要窄、行为要深”，避免切出一堆只传数据的浅模块；原子模块不必然“小”，但必须“再拆对调用方无益”。

## 怎么用

### 1. 安装

把这个仓库的 `SKILL.md` 放到你的 agent **skills 目录**。例如（DSH Desktop）：

```
<harness>/skills/module-contract/
└── SKILL.md
```

### 2. 触发

Skill 是 **model-invoked** 的：它在描述里携带触发词，当你或你的 agent 提到下面的词时会被自动唤起：

> 新增功能 · 模块化 · 接口卡 · 拆模块 · 复用 · 组合（拼凑） · 原子模块 · 复合模块 · 模块地图

也可以直接输入命令手动触发：`/module-contract`。

### 3. 决策模式

一切模块切分与复用决策，默认由你**确认**（给出模块列表 + 接口卡草案 + 复用建议，你点头才落卡）。若想让它自动决定，把汇总地图头部改成：

```
复用决策模式: auto
```

随时可切回 `confirm`。

## 工作流程

1. **定位项目根与既有知识**——读 `docs/modules/MODULE-MAP.md`，首次运行建骨架；领域词从项目的 `CONTEXT.md` 注入。
2. **读懂新需求**——明确这个功能要满足的行为边界。
3. **模块化**——切出候选**原子模块**，逐个过 **deletion test**、**窄接口**、**可深**判据；原子依赖接口 / seam 组合成**复合模块**，复合再过**复合删测**决定是否命名。
4. **复用分析（决策阶梯）**——从低破坏性到高逐档判断：**直接复用 → 复合重组 → 换 adapter → 扩展 → 最少新增原子**，最终归入决策轴四分类并记录理由。
5. **决策模式**——`confirm` 等你批准，`auto` 直接写卡。
6. **写接口卡**——每个模块一个文件 `docs/modules/<slug>.md`。
7. **更新 `MODULE-MAP.md`**——索引表 + Mermaid 依赖图（有出边 = 复合，无出边 = 原子）。
8. **保鲜核对**——尽量与代码 / 类型对照，核不上的标 `⚠ 待核对`。

# Module Map

## 词汇（取自 deep module + 本 skill 补充）

| 词 | 含义 |
|---|---|
| **Atomic module（原子模块）** | 不依赖其它项目模块接口的结构单元；下限由删测守，可深 |
| **Composite module（复合模块）** | 依赖其它模块接口、由原子/复合组合而成；依赖图里有出边 |
| **复合删测** | 删掉命名复合，编排顺序/约束会散到 ≥2 个调用方 → 命名；否则只写编排代码 |
| **Module** | 有接口和实现的任意粒度（函数 / 类 / 包 / 跨层切片） |
| **Interface** | 调用方要用对模块必须知道的一切（签名 + 不变量 + 顺序 + 错误模式…） |
| **Seam** | 接口所在的、可替换行为的位置 |
| **Adapter** | 在 seam 处满足某接口的具体实现 |
| **Depth / Leverage** | 每学一单位接口能驱动多少行为；接口越窄、行为越深，越好 |
| **Deletion test** | 删掉模块：复杂度消失则多余，散布到 N 个调用方则值得留下 |

## 设计决策

- **只管设计，不写实现**：接口卡要当“单一事实来源”，必须与实现解耦。
- **通用，不绑定某项目**：路径相对当前仓库（`docs/modules/…`），领域词从当前项目 `CONTEXT.md` 注入。
- **可机器验证**：接口卡给出可判 “对/不对” 的验收依据，配合类型检查与契约测试形成验证闭环。
- **组合优先**：动工前先查地图，能直接复用就复用，能靠现有原子拼出新复合就不新建，最后才考虑新增原子。
- **结构轴 / 决策轴分离**：原子/复合描述“模块长什么样”，四分类描述“这一步怎么处置”，不新增并行词汇。
